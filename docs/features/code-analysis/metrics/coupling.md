# Coupling Metrics

## Overview

Coupling Metricsは、ソースコード内のクラスやモジュールが、ほかの要素にどの程度依存しているかを定量的に把握するための指標です。

依存関係の数や循環依存を計測することで、変更時に影響を受ける可能性のある箇所や、モジュール間の依存構造を確認できます。

以下の3つの指標を提供します。

| 指標 | 説明 | 基本計測単位 |
|---|---|---|
| CBO | クラスが依存する他クラスの数 | Class |
| Fan-out | モジュールが依存する他モジュールの数 | File |
| Dependency Cycles | モジュール間の循環依存グループ数 | Project |

CBOはクラス間、Fan-outとDependency Cyclesはモジュール間の依存関係を対象とします。

計測単位や集計に関する共通ルールは[Metrics](./README.md)を参照してください。

## Dependency Resolution

Coupling Metricsでは、ソースコードから静的に確認できる依存関係を対象とします。

### Measurement Rules

- `import`や`from ... import ...`による依存関係を対象とします。
- 継承、型注釈、インスタンス生成、属性参照、メソッド呼び出しなどから確認できる依存関係も対象とします。
- 絶対importと相対importは、解決できる場合、同じ依存先として扱います。
- importの別名は元の依存先に対応付けます。
- 同じ依存先への複数の参照は重複して計数しません。
- 自分自身への依存は計数しません。
- 実行時の値によって依存先が変化する場合、静的に確定できる依存先のみ計数します。

依存関係の数は参照回数ではなく、識別できた依存先の数を表します。

依存先は、参照元のスコープおよびimportの解決結果から一意に対応付けられる場合のみ確定とします。単純な名前・属性名が一致するだけでは同じ依存先とみなしません。`from package import name`で`name`がサブモジュールか属性か確定できない場合も、推測して数えず未解決として記録します。

本仕様の依存関係は静的な参照関係を意味し、実行時に必ず呼び出されることや読み込まれることを意味しません。

### Unresolved Dependencies

依存先を静的に特定できない場合、その参照を確定した依存関係として計数しません。

未解決情報には、可能な範囲で以下を記録します。

- 参照元
- 参照箇所
- 参照内容
- 解決できなかった理由

未解決の参照が存在しても、特定できた依存関係の計測は継続します。未解決情報には、静的解析の限界により特定できない参照と、解析処理自体が失敗した箇所を区別して記録します。特定できた依存数は下限となり得るため、未解決情報がある場合は完全な依存数として扱いません。

ただし、すべての動的な属性アクセスを未解決の依存として扱う必要はありません。クラスまたはモジュールへの依存を示す参照で、依存先を識別できなかったものを対象とします。

## CBO

### Definition

CBO（Coupling Between Objects）は、クラスがほかのクラスとどの程度結合しているかを表す指標です。

本仕様では、対象クラスから静的に確認できる他クラスへの依存数として計測します。

異なる依存先クラスの数を計測するため、同じクラスを何度参照しても1件として扱います。

### Measurement Rules

- クラス単位で計測します。
- 継承、型注釈、インスタンス生成、属性参照、メソッド呼び出しなどを対象とします。
- クラス内のメソッドで確認できる依存も、所属クラスの依存として扱います。
- 同一クラスへの複数の参照は1件として計数します。
- 継承と型注釈など、異なる方法で同じクラスを参照しても1件とします。
- 同じモジュール内の他クラスへの依存も計数します。
- 外部モジュールで定義されたクラスへの依存も計数します。
- 自クラスへの参照は計数しません。
- 静的に依存先クラスを特定できない参照は計数せず、未解決情報として記録します。
- 他クラスへの依存が確認できない場合は0とします。

クラスの識別には、単純なクラス名ではなく、解決可能なモジュールとクラスの定義位置を使用します。モジュール内での同名クラスの再定義は別の定義位置として識別します。

同名でも異なるクラスへの依存は、それぞれ計数します。

### Boundary Cases

| ケース | 期待される動作 |
|---|---|
| 他クラスへの依存がない | `0` |
| 1つのクラスを1回参照 | `1` |
| 同じクラスを複数回参照 | `1` |
| 継承と型注釈で同じクラスを参照 | `1` |
| 異なる2クラスを参照 | `2` |
| 同じモジュール内の他クラスを参照 | 計数する |
| importの別名を使用 | 元のクラスへの依存として計数 |
| 自クラスを参照 | 計数しない |
| 依存先の型を特定できない | 確定値に加算せず未解決情報に記録 |
| クラスが存在しない | 平均・最大は`null` |

### Example

```python
class Repository:
    def save(self):
        pass


class Logger:
    def info(self, message):
        pass


class Service:
    def __init__(self, repository: Repository, logger: Logger):
        self.repository = repository
        self.logger = logger

    def execute(self):
        self.repository.save()
        self.logger.info("Saved")
```

計測結果：

| クラス | CBO | 依存先 |
|---|---:|---|
| Repository | 0 | なし |
| Logger | 0 | なし |
| Service | 2 | Repository、Logger |

`Service`は`Repository`と`Logger`を複数箇所で参照していますが、それぞれ1件として計数するため、CBOは2となります。

## Fan-out

### Definition

Fan-outは、モジュールが依存している他モジュールの数を表す指標です。

本仕様では、解析対象の各Pythonファイルを1モジュールとして扱い、静的に確認できる異なる依存先モジュールの数を計測します。外部モジュールも一意に識別できる場合は依存先に含めます。

### Measurement Rules

- モジュール単位で計測します。
- `import`、`from ... import ...`を対象とします。
- 継承、型注釈、関数呼び出しなどから依存先モジュールを確認できる場合も対象とします。
- 同じモジュールへの複数の参照は1件として計数します。
- `from package import name`は、`name`がモジュールとして確定できた場合はそのモジュールを、属性として確定できた場合はその定義元モジュールを計数します。判別不能な場合は推測せず未解決として記録します。
- 標準ライブラリや外部ライブラリへの依存も対象とします。
- 解析対象外のモジュールへの依存も、静的に特定できる場合は計数します。
- 同一モジュール内で完結する参照は計数しません。
- 静的に依存先モジュールを特定できない参照は未解決情報として記録します。
- 他モジュールへの依存が確認できない場合は0とします。

モジュールの識別には、解決可能なモジュール名または定義元を使用します。

同じモジュールを異なるimport形式や別名で参照しても、依存先は1件として扱います。

### Boundary Cases

| ケース | 期待される動作 |
|---|---|
| 他モジュールへの依存がない | `0` |
| 1モジュールへの依存 | `1` |
| 同じモジュールを複数回import | `1` |
| 同じモジュールから複数の関数をimport | `1` |
| 絶対importと相対importで同じ対象を参照 | `1` |
| importの別名を使用 | 元のモジュールへの依存として計数 |
| 標準ライブラリへの依存 | 計数する |
| 外部ライブラリへの依存 | 計数する |
| 自モジュールへの参照 | 計数しない |
| 動的importで依存先を特定できない | 未解決情報として記録 |
| モジュールが0件 | 平均・最大は`null` |

### Example

```python
import json
import logging
from pathlib import Path
from pathlib import PurePath
```

計測結果：

`Fan-out = 3`

依存先：

- `json`
- `logging`
- `pathlib`

`pathlib`から複数の要素をimportしていますが、依存先モジュールは同じため1件として計数します。

## Dependency Cycles

### Definition

Dependency Cyclesは、モジュール間に存在する循環依存を検出する指標です。

循環依存とは、あるモジュールから依存関係をたどることで、再び元のモジュールへ到達できる状態を指します。

本仕様では、循環依存に関係するモジュール群を検出し、そのグループ数を計測します。

### Measurement Rules

- モジュール単位で循環依存を検出します。
- 解析対象内のモジュール間の依存関係を対象とします。
- 解析対象外のモジュールは循環依存の検出対象に含めません。
- 静的に確認できる依存関係のみ使用します。Fan-outと同じ依存解決規則を用いますが、循環の判定対象は解析対象内のモジュールに限定します。
- 依存関係の方向を考慮します。
- 相互に到達可能な2つ以上のモジュールを、1つの循環依存グループとして扱います。
- 同じグループ内に複数の循環経路が存在しても、グループ数は1とします。
- 循環に関係するモジュール群を取得できるものとします。
- 循環経路をすべて列挙する必要はありません。
- 循環依存が存在しない場合は0とします。

循環依存グループは、依存関係を表す有向グラフの強連結成分に基づいて定義します。

なお、自モジュールへの参照は依存関係として計数しないため、単一モジュールによる自己参照は循環依存グループに含めません。

### Boundary Cases

| ケース | 期待される動作 |
|---|---|
| 循環依存がない | `0` |
| A → B → A | 1グループ |
| A → B → C → A | 1グループ |
| 同じモジュール群に複数の循環経路 | 1グループ |
| 独立した循環依存が2組ある | 2グループ |
| A → B → Cの一方向のみ | `0` |
| 単一モジュールの自己参照 | 計数しない |
| 解析対象外のモジュールを経由する循環 | 検出対象外 |
| モジュールが0件 | `0` |

### Example

以下の3モジュールが存在するとします。

```text
a.py → b.py
b.py → c.py
c.py → a.py
```

この場合、`a.py`、`b.py`、`c.py`は互いに到達可能です。

計測結果：

| 項目 | 結果 |
|---|---|
| Dependency Cycles | 1 |
| 循環依存グループ | `a.py`、`b.py`、`c.py` |

また、次の関係が存在する場合、

```text
a.py ↔ b.py

c.py ↔ d.py
```

計測結果は2グループとなります。

## Aggregation

Coupling Metricsは、指標の基本計測単位に応じて集計します。

| 指標 | 基本計測単位 | Average | Maximum | その他 |
|---|---|---|---|---|
| CBO | Class | ○ | ○ | クラスごとの依存先 |
| Fan-out | File | ○ | ○ | モジュールごとの依存先 |
| Dependency Cycles | Project | — | — | 循環依存グループ数と構成 |

CBOの平均値・最大値は、対象範囲内のクラスの計測値から算出します。

Fan-outの平均値・最大値は、対象範囲内のモジュールの計測値から算出します。

Dependency Cyclesは解析対象全体に対して検出し、グループ数を提供します。

クラスまたはモジュールが存在しない場合、対応する平均値・最大値は`null`とします。

Dependency Cyclesについて、解析対象モジュールが存在しない場合は0とします。

集計に関する共通ルールは[Metrics — Aggregation](./README.md#aggregation)を参照してください。

## Limitations

- 静的解析で特定できない実行時の依存関係は、確定した依存関係として計数しません。
- 動的import、動的属性アクセス、実行時の型変更などによって、実際の依存関係と計測結果が異なる場合があります。
- CBOとFan-outは、依存関係の数を計測するものであり、依存先の変更頻度や依存の強さを直接表すものではありません。
- CBOは本仕様では依存元から依存先への方向を持つ指標として定義しています。双方向の結合を計数する方式とは結果が異なる場合があります。
- Dependency Cyclesは静的な依存関係に基づくため、実行時の循環的な呼び出し関係を検出するものではありません。
- 循環依存が存在することだけで、必ずしも実行時エラーが発生するわけではありません。
- 計測結果の比較では、依存先の解決条件や解析対象範囲が一致していることを確認する必要があります。
