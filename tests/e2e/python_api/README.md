# Python API E2Eテストケース

## 目的と前提

公開Python APIを利用者と同じ方法で呼び出し、外部仕様への適合性を検証する。
仕様のSingle Source of Truthは[Code Analysis](../../../docs/features/code-analysis/README.md)とする。
このREADMEはテスト設計であり、新たなAPIや計測規則を定義しない。

- 公開入口は`from cqa import analyze, compare, load_analysis_result`と、`cqa`からインポートする公開データモデル・変換メソッドとする。
- 入力は実際のソースファイル・ディレクトリ、保存済みJSON、公開モデルで作成・変更した解析結果とする。
- 観測対象は公開された返却値・例外・入力ファイルへの副作用とする。
- 非公開モジュール、内部クラス、AST、探索順、内部関数の呼び出し回数には依存しない。解析・依存解決・ファイル処理をmockで置き換えない。
- 返却値は公開dataclassの属性として参照する。公開された型・フィールド・参照関係を検証し、非公開の表現には依存しない。表中の`null`はPythonでは`None`、JSON変換後は`null`を表す。
- 期待値は仕様と入力コードから独立して決める。CLIとの一致や、採用ライブラリと同じ値であることだけを合否判定にしない。
- 各表の行はケース群。同じ行に列挙した入力は個別に実行する。仕様未確定の入力は末尾に分離する。

## テストデータと実行条件

- ファイル名・関数名・クラス名だけでなく、返却される定義位置と包含関係を確認できる小さなプロジェクトを使う。
- Git規則のケースは一時的なリポジトリで実行し、ユーザー環境のGit設定から隔離する。
- アクセス権のケースは実際のOS権限で再現する。権限を制限できない環境では、理由を示して対象ケースをスキップする。
- 文字列比較は仕様で定めたコードを対象とし、固定されていない説明文・並び順は一致を要求しない。
- 浮動小数点数は表示丸めと数値型の表現誤差を区別する。仕様で保証しない完全なビット一致を要求しない。
- 重複の入力は比較対象トークンを数え、意図しない別の50トークン一致を含まないことを確認する。

## Complexityの計測ケース

根拠：[Complexity](../../../docs/features/code-analysis/metrics/complexity.md)。CCはCyclomatic、CogはCognitive、DepthはNestingを表す。
加算構文の単独入力には、ほかの加算構文を混ぜない。

| ID | 種別 | 条件・入力 | 期待結果 |
|---|---|---|---|
| API-X01 | 境界 | 分岐・再帰のない関数 | CC=1、Cog=0、Depth=0 |
| API-X02 | 正常 | `if`、`if-else`、`if-elif`を個別に配置 | CCは2・2・3。Cogは最初の2入力で1・2。Depthはすべて1 |
| API-X03 | 正常 | `for`・`async for`・`while`・`with`・`async with`を個別に配置 | CC=2、Depth=1。ループに`else`を付ける入力ではCC=3 |
| API-X04 | 正常 | `try`と例外ハンドラをN件配置する。通常ハンドラと`except*`を別入力にする | CC=1+N。`try-else`追加でさらに+1、`finally`の追加は+0。兄弟節だけならDepth=1 |
| API-X05 | 境界 | `try-finally`のみ | CC=1、Depth=1 |
| API-X06 | 正常 | `assert`、条件式を個別に配置する | CC=2。条件式のみのDepthは0 |
| API-X07 | 正常 | `if a and b`、`if a and b or c` | CCは3・4。演算子ごとの加算を確認する |
| API-X08 | 正常 | リスト・集合・辞書内包表記、ジェネレータ式に既知数の`for`・`if`節を配置する | CCは1+for節数+if節数。Depthは0 |
| API-X09 | 境界 | 通常caseをN件と無条件`case _`、およびガード付き`case _`を別入力にする | 通常caseは各+1、無条件ワイルドカードは+0、ガード付きはcase分+1。ガードの論理演算子も各+1。Depthは1 |
| API-X10 | 正常 | `if`内`if`、`for`内`if`を個別に配置する | CC=3、Cog=3、Depth=2 |
| API-X11 | 境界 | 深さ2の分岐内に`elif`・`else`を置く | 対応する`if`と同じ深度2を維持し、節ごとに深度を増やさない |
| API-X12 | 境界 | 外側に分岐なし、内側関数に`if`1つ | CCは外1・内2、Depthは外0・内1。Cogには別モデルのネスト関数規則があるため、この期待値を転用しない |
| API-X13 | 境界 | モジュール・クラス本体にのみ分岐があり、メソッド本体にはない | 関数のCCは1。クラス自体のCCスコアを作らない |
| API-X14 | 正常 | 通常関数と同じ本体をasync・特殊・static/classメソッドに置く | 関数として個別に計測する。lambdaのみでは独立したCC計測対象を作らない |
| API-X15 | 正常 | 深さ1の構造を複数並べる入力と、`while`内`with`の入力 | Depthは順に1・2。構造数の合計にしない |
| API-X16 | 正常 | 分岐・論理式・再帰を含まない通常の関数／メソッド呼び出し | 呼び出し自体によるCogの加算は0 |

SonarSourceに委ねられたCogの論理演算子・再帰・ネスト関数・match等と、Radonの複数行文字列分類は、末尾の確認事項で期待値の確定待ちとして管理する。

各テストのdocstringに対応IDと観点を記載している。各行はケース群の対応表であり、
仕様確認待ちの入力は上の「仕様確認後に期待値を確定するケース」に従う。
外部ライブラリ・再エクスポート・判別不能なimport等の入力は、依存解決環境と規則の確定後に追加する。

入力ファイル作成・実OSの権限制限・JSON破損データ・トークン境界の入力生成には、既存CLIテストの補助処理を再利用する。
APIの返却値は公開モデルの属性を直接検証し、CLIを代替の解析入口にしない。
共通補助処理を安定してimportするため、`tests`と`tests/e2e`をパッケージとしている。
権限エラーをOS上で再現できない環境と、Gitやリンクの作成機能が利用できない環境では、該当テストだけ理由付きでスキップする。
